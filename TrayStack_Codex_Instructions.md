# TrayStack — Implementation Instructions for Codex

> **Audience:** Codex, acting as the implementation engineer in a new or existing repository.  
> **Goal:** Build a working, demonstrable document-ingestion, variant-management, and search application for a Riverty technical case study.  
> **Priority:** A complete, tested vertical slice is more important than the number of frameworks or features used.  
> **Project name:** **TrayStack**.

## 0. Working instructions for Codex

1. Inspect the repository before changing anything. Preserve relevant existing files, conventions, licenses, and user work. If the repo is empty, initialize it as specified below.
2. Implement the application, not just a design. Make reasonable implementation decisions without repeatedly asking for approval. If a decision is not specified, choose the simplest maintainable approach and document it.
3. Follow the **milestones in order**. Get the minimum end-to-end workflow running before tackling optional capabilities.
4. Use established libraries, clear types, migrations, automated tests, and explicit error handling. Do not create elaborate abstractions that have no current purpose.
5. **Do not silently fake functionality.** If OCR, a conversion, indexing, or a query fails, show a real failure/partial-status result; never use placeholder search results in the running application.
6. Do not require paid cloud services, API keys, LLMs, embeddings, or external network calls at runtime. A laptop and Docker should be enough for the core demonstration.
7. Keep original input bytes immutable. All derived content must be traceable to its source artifact and processing method.
8. Run relevant checks and tests after implementing each milestone. Fix failures rather than merely reporting them. At the end, explain what works, what was tested, what remains incomplete, and the exact commands to launch and demo the app.
9. Favor user-visible functionality and correctness over polishing infrastructure. In particular, implement the search semantics carefully; the challenge is about finding contracts that **do or do not contain** specified passages.
10. If the working environment cannot run Docker or download dependencies, still implement the real files, migrations, tests, and documentation; report the blocker precisely. Do not claim to have run tests that could not be run.

## 1. Product context and goals

TrayStack stores logical documents and multiple **revisions** and **representations (artifacts)** of each revision, then makes their contents searchable and reviewable through a web UI and REST API.

Example representations of the *same revision*:

- Original JPEG image (possibly handwritten or scanned).
- Original scanned PDF without an embedded text layer.
- PDF containing searchable text (originally digital or generated by OCR).
- Structured extraction JSON.
- Extracted Markdown.
- Normalized Markdown.
- Canonical, indexed plain text, with page information.

A revised or renegotiated contract is a **new revision**, not merely another file representation of the old revision. Two different OCR runs on the same source are two artifacts, not two contract revisions.

The motivating Riverty case study describes contracts on SharePoint, PDFs and old scanned/handwritten JPEG files, and lawyers looking for contracts missing a specified text passage or containing a company name requiring an update. The requested delivery is a technical solution plus a basic document-processing pipeline and simple frontend. Riverty's mentioned environment includes Azure, Python/FastAPI, React/TypeScript and containerized services. **The case study does not require RAG, a knowledge graph, an LLM, or a particular search engine.**

### Primary user stories

1. As a user, I can create a document, set its title and optional metadata, and upload a PDF or JPEG as its first revision's original artifact.
2. I can see all documents, their revisions, artifacts, processing states and metadata.
3. I can upload another representation of an existing revision **without** mistakenly creating a new revision.
4. I can create a new revision of a document when the contract's content changes.
5. I can launch document processing and see the resulting artifacts: extracted/normalized Markdown, structured extraction data, and searchable text.
6. I can retrieve or download any stored artifact, including the exact original bytes.
7. I can search for a literal text passage, including one that spans lines or pages.
8. I can search for approximate textual matches caused by OCR errors, using a clear similarity threshold, and inspect the corresponding text and location.
9. I can search for documents **not containing** a literal passage, but the app must distinguish a genuine negative result over fully processed text from a document that could not be reliably examined.
10. I can inspect why a result was returned: matched text, snippet, document, revision, page if known, and the extraction/processing status.

### Non-goals for the first working version

- No autonomous AI agents, LangChain/LangGraph, RAG, embedding model, or knowledge graph.
- No legal judgement about whether two clauses are juridically equivalent.
- No integration with real Riverty SharePoint or their restricted archival REST API.
- No modifying contractual PDFs in place or producing a signed/amended contract.
- No enterprise authentication, complicated user roles, Kubernetes, or distributed search clusters.
- No claim that an OCR result is legally authoritative.

These are deliberate boundaries, not missing architecture. The system should be extensible without building speculative functionality prematurely.

## 2. Technology choices

Use the following default stack, unless the existing repository already has a clearly compatible equivalent:

| Layer | Preferred choice | Notes |
|---|---|---|
| API | Python 3.12+ / FastAPI / Pydantic v2 | OpenAPI docs automatically exposed |
| Persistence | PostgreSQL 16+ | Relational data, JSONB metadata, full-text capabilities, `pg_trgm` |
| ORM + migrations | SQLAlchemy 2.x + Alembic | Prefer explicit, understandable queries |
| PostgreSQL driver | psycopg 3 | Consistent with SQLAlchemy |
| Object storage (MVP) | Local filesystem behind a storage interface | Volume shared by API and worker; later Azure Blob Storage |
| PDF text extraction | PyMuPDF | Fast extraction, per-page details and positions |
| Image/scanned PDF OCR | Tesseract / pytesseract | Offline baseline; add other engines later |
| Structured document conversion | Docling (optional/secondary processor) | Rich document structure; avoid making first run depend on downloading large models |
| Fuzzy matching | PostgreSQL `pg_trgm` + RapidFuzz | Index candidate passages; verify final alignments |
| Web app | React + TypeScript + Vite | Simple SPA, native fetch or a small typed API client |
| Styles | Lightweight CSS | Avoid a large UI component dependency for the demo |
| Packaging | Docker Compose | PostgreSQL, API, worker, frontend; persistent volumes |
| Python tests | pytest | Include real PostgreSQL integration tests |
| Frontend checks | TypeScript typecheck + Vitest if practical | At minimum build successfully |

**Important:** Do not use SQLite as a quiet substitute for PostgreSQL search. `pg_trgm` and the SQL semantics are part of the solution. A SQLite-only test suite is insufficient.

Use a Python lock/dependency mechanism (`uv` preferred if available, otherwise standard `pip` tooling) and a checked-in frontend lockfile. Select mutually compatible versions rather than assuming old library examples still work.

```text
          v

          |                                  documents
          |                                  revisions
          v                                  artifacts metadata
    Storage interface                        jobs / pages / search texts
          |
          v
    Local blob directory
          ^
          |
    Processing worker <---------------------- processing_jobs
          |
          +--> inspect original / PDF text extraction / OCR
          +--> structured extraction data + Markdown
          +--> normalized Markdown + canonical text
          +--> persist pages + index searchable text
```

- API handles uploads, metadata, downloads, search requests, and processing-job creation.
- Worker performs slow or CPU-intensive document processing **outside HTTP request handling**.
- PostgreSQL is authoritative for identities, relationships, revision selection, processing state, page text, and search metadata.
- Blob storage is authoritative for immutable artifact bytes. Never embed entire PDFs/images in PostgreSQL.
- No Redis/Celery is required for the MVP. A simple database-backed worker is acceptable and should be documented as such.

## 4. Core data model

Design and implement Alembic migrations for these entities. Use UUID primary keys, foreign keys, appropriate uniqueness constraints, timestamps in UTC, and cascade/restrict rules appropriate to immutable artifacts.

### 4.1 `documents`

- `id` UUID primary key
- `title` string, nonempty
- `metadata` JSONB, default `{}` (e.g. contract type, company, tags, source system)
- `created_at`, `updated_at`

A document is a logical contract or other logical item, independent of the file format.

### 4.2 `revisions`

- `id` UUID primary key
- `document_id` UUID FK to documents
- `revision_number` positive integer
- `label` nullable string (e.g. `signed`, `amended-2026`)
- `created_at`
- UNIQUE(`document_id`, `revision_number`)

The most recent revision is the highest revision number unless the user explicitly chooses another. Default search scope is **latest revision per document**; provide a documented option for all revisions later if easy.

### 4.3 `artifacts`

- `id` UUID primary key
- `revision_id` UUID FK to revisions
- `source_artifact_id` nullable UUID FK to another artifact in the same revision
- `kind`: role such as `original`, `ocr_pdf`, `structured_json`, `extracted_markdown`, `normalized_markdown`
- `mime_type` (e.g. `application/pdf`, `image/jpeg`, `text/markdown`, `application/json`)
- `original_filename` nullable display field
- `storage_key`: opaque **relative** storage key; never accept arbitrary paths from users
- `sha256` lowercase hexadecimal digest of exact stored bytes
- `size_bytes` integer
- `processor` nullable (`upload`, `pymupdf`, `tesseract`, `docling`, `normalize-markdown`)
- `processor_version` nullable string
- `parameters` JSONB default `{}`
- `created_at`

Artifacts are immutable. A new processing run may produce another artifact of the same `kind`, with its own identity. Keep their provenance; do not overwrite earlier artifacts or use `kind` as a uniqueness constraint. For the MVP, single-parent provenance is enough; document that a DAG with multiple inputs could be implemented later.

**Invariant:** `source_artifact_id`, when set, must refer to an artifact belonging to the same revision; guard against cycles if arbitrary parent selection is exposed.

### 4.4 `processing_jobs`

- `id` UUID primary key
- `revision_id` FK
- `source_artifact_id` FK
- `operation` (`extract_and_index`; additional operations optional)
- `status` (`queued`, `running`, `completed`, `failed`)
- `attempts`, `started_at`, `finished_at`, `created_at`
- `error_message` nullable, sanitized (no secrets or raw contract content)
- `result_artifact_ids` optional JSONB array or relationship

Worker should claim jobs transactionally. A simple `SELECT ... FOR UPDATE SKIP LOCKED` pattern is suitable if multiple worker instances exist. MVP may run only one worker, but it must never process the same job concurrently by mistake. Failed jobs should be visible and retryable.

### 4.5 `revision_texts`

One row per revision that has a currently selected canonical indexed text:

- `revision_id` PK/FK
- `source_artifact_id` pointing to the artifact that produced the indexed representation
- `plain_text` full extracted text (not interpreted as Markdown)
- `normalized_text` search normalization applied to the full text
- `status`: `complete`, `partial`, or `unavailable`
- `pages_total`, `pages_processed`, `pages_failed`
- `updated_at`

This table makes it possible to search the **entire processed document**, rather than relying on Top-k chunks. A negative search result is valid only within a clearly declared processing scope and quality state.

### 4.6 `page_texts`

- `id` UUID primary key
- `revision_id` FK
- `page_number` positive integer; page 1 for a JPEG
- `text` text
- `normalized_text` text
- `start_offset`, `end_offset` offsets into `revision_texts.normalized_text` if reliable
- `extraction_method` (`embedded_pdf_text`, `ocr`, etc.)
- `status` (`complete`, `partial`, `unavailable`)
- `confidence` nullable, only if the engine actually provides it
- optional `layout_metadata` JSONB for bounding boxes and structured provenance

Add uniqueness for (`revision_id`, `page_number`) for the chosen canonical run. If storing several alternative OCR runs, either store page records per run or replace only the **selected index** while retaining immutable source artifacts.

### 4.7 `search_segments`

Small searchable spans for efficient fuzzy candidate selection:

- `id` UUID primary key
- `revision_id` FK
- `page_number` nullable
- `sequence_number` integer
- `text`, `normalized_text`
- `start_offset`, `end_offset` in canonical normalized text if available

Prefer paragraphs/lines or sliding overlapping windows; **never rely on segments for proving absence**. Store enough context that candidates crossing boundaries can be reconstructed. A scan may contain OCR errors and those uncertainty details should remain visible.

### Indices and migration requirements

- `CREATE EXTENSION IF NOT EXISTS pg_trgm` through an Alembic migration.
- GIN trigram index on `search_segments.normalized_text` (`gin_trgm_ops`).
- Consider GIN trigram index on `revision_texts.normalized_text` for literal substring matching with `LIKE`/`ILIKE`, evaluating index size and query plans.
- Indices on foreign keys, revision numbers, job statuses, and timestamps as appropriate.
- A PostgreSQL full-text `tsvector` index is **optional**. It is for word-oriented search, not an exact replacement for phrase-substring matching.
- Keep migration code in source control; do not call `Base.metadata.create_all()` as the production migration strategy.

## 5. Artifact storage

Implement a `Storage` interface with at least:

- `put_bytes(data: bytes, mime_type: str) -> StoredBlob`
- `open` or streaming retrieval for an opaque storage key
- `exists(storage_key)`

MVP implementation: local filesystem under a configurable directory such as `/data/blobs/`, ideally content-addressed by SHA-256 (e.g. `ab/cd/<sha256>`). Multiple artifacts may reference the same content-addressed blob; do not lose individual artifact provenance and metadata.

Requirements:

- Verify SHA-256 on ingestion.
- Use atomic writes (temporary file + rename) rather than partially visible blobs.
- Only return files referenced by an authorized artifact ID; do not expose arbitrary paths or accept traversal sequences.
- Preserve original filename separately for display/download; sanitize response headers.
- Implement an explicit maximum file size (e.g. configurable 25 MB for the demo) and allowlisted MIME/extensions. Validate actual file signatures where feasible, not just client-provided MIME.
- Store credentials in environment variables, never in Git.
- Support `application/pdf`, `image/jpeg`, `image/png` in the first upload workflow; derivatives also include Markdown and JSON.

Azure Blob Storage can be represented by a future adapter, but do not implement it at the cost of the MVP.

## 6. Document processing pipeline

Implement real, idempotent-ish processing, preferably as a small series of explicit functions with tests.

### Pipeline steps

1. **Inspect source artifact**: validate file type, hash, size and metadata. Record whether PDF pages contain substantial embedded text.
2. **Extract per page**:
   - Digital PDF: PyMuPDF `page.get_text(...)`; preserve page boundaries and, where practical, word/block coordinates from `page.get_text("words")` or `"blocks"`.
   - Scanned or textless PDF pages: render pages and run Tesseract OCR. Make OCR language configurable (default English; add German when language pack installed).
   - JPEG/PNG: use Tesseract OCR directly.
   - For mixed PDFs, choose extraction per page; don't assume all pages behave alike.
3. **Assess extraction status**: identify failed/empty/suspicious pages. An empty page with actual image content must not quietly count as successfully processed empty text. Mark `partial`/`unavailable` when appropriate. Heuristics are imperfect; be conservative and document limits.
4. **Build a structured result** containing page number, extracted text, extraction method, and optional blocks/bounding boxes; serialize to a `structured_json` artifact.
5. **Generate extracted Markdown** retaining paragraph breaks and page awareness where possible. Basic valid Markdown is fine. Do not invent headings or clauses based solely on guesses. If Docling is enabled, its structure can improve Markdown generation.
6. **Generate normalized Markdown** as a separate immutable artifact. Preserve readable structure; use reversible or explicitly documented transformations where possible.
7. **Build canonical text** and search segments; write `revision_texts`, `page_texts`, and `search_segments` consistently in a database transaction. Page offsets should refer to the exact normalized string saved in the database.
8. **Mark the job completed** only when derived artifacts and database index have been committed and are mutually consistent. On error, mark failed, retain originals, and make retry possible.

### Normalization: define precisely

Implement and unit-test a deterministic `normalize_for_search(text)` with a documented stable sequence, for example:

1. Unicode normalization (choose NFC or NFKC deliberately, document consequences).
2. Normalize line endings.
3. Repair clearly recognized line-break hyphenation (`confiden-\ntial` -> `confidential`), with an option to disable when ambiguous.
4. Collapse whitespace runs to one space while preserving token order.
5. Case-fold for a case-insensitive search mode.

**Do not** remove numbers, negations, words such as `shall not`, punctuation that may convey obligations, or arbitrary legal wording. Retain raw extracted text as a separate representation. Exact mode must search the original/extracted text according to precisely documented rules; normalized mode may ignore harmless whitespace/case differences.

### OCR handling

- Tesseract is a baseline for **printed** scans, not a guarantee for handwriting. For old cursive handwriting, record a warning or `partial`/`unavailable`; never claim reliable extraction unless actually validated.
- OCR confidence is optional; only populate it from real provider output. Do not invent scores.
- A scanned PDF with OCR does **not** automatically require synthesizing a new PDF with a text layer. Producing a true searchable `ocr_pdf` artifact (e.g. with OCRmyPDF) is a **stretch goal**. If it is not generated, do not label the original PDF as searchable.
- Docling is a useful optional higher-quality converter. If implemented, use its current documented API (`DocumentConverter().convert(path).document`; `export_to_markdown()`, `export_to_dict()`). Keep an easy reliable fallback and do not assume Docling's OCR/model setup is fast on every machine.
- For the demo, direct extraction + optional OCR is more important than perfect layout fidelity.

### Reprocessing and provenance

A reprocessing run should not mutate source files. It may produce new artifacts and select a new current canonical index for the revision. Keep earlier artifacts and document which processor and parameters produced the selected index. If a run fails midway, old valid search results should remain intact or the index should clearly reflect a failed/unavailable state, never an inconsistent mixture.

## 7. Search: the critical functional requirement

Implement **three distinct text-matching semantics**:

### A. Exact literal match (`exact`)

Find the exact string in extracted text. Decide and document whether exact mode includes line-break normalization; the preferred choice is truly literal matching on the canonical raw extracted text, with a separate normalized mode for whitespace/case differences. Return all useful offsets/page references and a snippet.

### B. Normalized literal match (`normalized`)

Apply the **same** deterministic normalization to query and indexed text. Detect contiguous substring occurrence, including matches crossing line breaks and (if correctly mapped) page boundaries. A result means the normalized phrase occurred, not that it was legally equivalent.

For performance, use PostgreSQL indices where applicable, but first ensure correctness. A `LIKE`/`strpos` query over the complete canonical normalized text can be acceptable in the demo. Escape wildcard characters when using `LIKE`; prefer bound parameters.

### C. Approximate wording (`fuzzy`)

Designed primarily for OCR mistakes and small textual variations, **not** semantic equivalence:

1. Retrieve candidates using a `pg_trgm` index over `search_segments.normalized_text`. Consider `word_similarity()` or `strict_word_similarity()` for phrase-in-passage retrieval; compare behavior with `similarity()` instead of assuming one is best.
2. Reconstruct neighboring spans if necessary, so phrases crossing segment boundaries are not inadvertently lost.
3. Rerank candidates with RapidFuzz (`partial_ratio_alignment` or a suitable edit-distance based algorithm); return actual matched text, alignment/offset if reliable, and a clearly named similarity score.
4. A score threshold must be configurable (e.g. input in range 0.0–1.0, translated to RapidFuzz's 0–100 scale). Display it as **text similarity**, never probability of correctness or legal equivalence.
5. Differences in amounts, dates, names and negations can be critical. Fuzzy hits should always be labeled **possible matches requiring review**. If practical, prominently highlight these differences.
6. Very short queries and queries consisting mainly of punctuation/digits need explicit handling; trigram filtering may be ineffective. Do not silently return incorrect "not found" results.

### Search for absence (`lacks`)

**This must be handled differently from positive Top-k retrieval.**

For a specified exact or normalized literal query:

- Determine the eligible revision scope (latest revision of each document by default).
- For each revision, search the **entire canonical extracted text**, not just the top-ranked segments.
- Split outcomes into:
  1. `found` — phrase present in the selected text;
  2. `not_found_in_processed_text` — phrase not present **and** the selected extraction status is `complete`;
  3. `unverifiable` — no text, incomplete extraction, failed OCR, or missing processing.
- For `relation: "lacks"`, list `not_found_in_processed_text` as the negative matches and show `unverifiable` separately as a warning group. Avoid stating simply "clause missing" or "contract compliant".
- `lacks` with `fuzzy` is **not required in the MVP** because no fuzzy candidate above a threshold is not proof of absence. Either return an explicit 422 validation error with explanation or implement a carefully labeled `no_possible_match_above_threshold` result that remains nondefinitive. Prefer 422 for the MVP.

Do **not** use an LLM, embeddings, or a graph index to claim absence of a literal phrase. This is a deterministic full-text problem once extraction quality is established.

### Search response contract

For a positive result include:

- `document_id`, title, `revision_id`, revision number
- `artifact_id` or canonical extraction provenance
- `mode` (`exact`, `normalized`, `fuzzy`)
- `status` (`found`, `possible_match`, etc.)
- `matched_text` and concise `snippet`
- `page_number` if known
- `start_offset`, `end_offset` if reliably known
- `score` nullable (null for exact; fuzzy scoring only for fuzzy)
- extraction-quality information and any relevant warning

Do not invent page numbers or offsets when unavailable. If exact highlighting is difficult, provide a page jump and textual snippet first, and document the limitation.

### Why this design

A trigram index is good for *finding candidate text passages even with OCR errors*. It is not a replacement for exact full-document verification. Likewise, arbitrary embeddings and semantic chunks are not necessary for the task of finding contracts without a **particular text passage**.

## 8. REST API

Use `/api` prefix. Make request and response schemas explicit with Pydantic, and expose `/docs` as FastAPI's interactive OpenAPI documentation.

Suggested endpoints (adapt details consistently as needed):

| Method / path | Behavior |
|---|---|
| `GET /api/health` | Health/readiness information; identify DB failure honestly |
| `POST /api/documents` | Create document with title and metadata |
| `GET /api/documents` | Paginated document list, title/metadata/status summary |
| `GET /api/documents/{document_id}` | Document details, revisions, artifacts |
| `PATCH /api/documents/{document_id}` | Update title/metadata only |
| `POST /api/documents/{document_id}/revisions` | Create content revision |
| `GET /api/revisions/{revision_id}` | Revision and processing status |
| `POST /api/revisions/{revision_id}/artifacts` | Multipart upload of PDF/JPEG/PNG/derived variant; default kind `original` |
| `GET /api/revisions/{revision_id}/artifacts` | List stored variants and provenance |
| `GET /api/artifacts/{artifact_id}` | Artifact metadata |
| `GET /api/artifacts/{artifact_id}/content` | Stream/view/download exact stored bytes |
| `POST /api/revisions/{revision_id}/process` | Enqueue extraction/indexing of specified original artifact |
| `GET /api/jobs/{job_id}` | Processing status, errors, outputs |
| `POST /api/jobs/{job_id}/retry` | Retry failed job (if feasible) |
| `POST /api/search` | Search across chosen revision scope |

For convenience, a single combined `POST /api/documents/upload` endpoint may create a document, revision and original artifact, but it must use the same underlying services as the explicit endpoints.

### Example upload flow

```text
POST /api/documents             -> document_id
POST /api/documents/{id}/revisions -> revision_id
POST /api/revisions/{id}/artifacts (multipart: file=contract.pdf, kind=original)
POST /api/revisions/{id}/process   -> 202 Accepted, job_id
GET  /api/jobs/{job_id}            -> queued/running/completed/failed
GET  /api/documents/{id}          -> all generated artifacts
```

### Example search request

```json
{
  "query": "The receiving party shall not disclose confidential information",
  "mode": "normalized",
  "relation": "lacks",
  "scope": "latest",
  "limit": 50
}
```

An example of **fuzzy positive** search:

```json
{
  "query": "Riverty GmbH",
  "mode": "fuzzy",
  "relation": "contains",
  "threshold": 0.82,
  "scope": "latest",
  "limit": 50
}
```

The first search might yield multiple `not_found_in_processed_text` results **and** a separate `unverifiable` count/list. The second yields `possible_match` results with similarity scores and textual evidence.

### API correctness rules

- Validate file types and input lengths, JSON metadata shape, `threshold` range, pagination, and UUIDs.
- Use 201 for created resources, 202 for queued jobs, 404 for unknown objects, 409 for revision/job conflicts, 422 for unsupported search combinations or invalid input.
- Use streaming for downloads; don't load huge files into memory merely to send them.
- No unrestricted filesystem endpoints; prevent path traversal and SQL injection.
- CORS configured specifically for the local frontend origin, not indiscriminately wide-open as a production default.
- API metadata must not contain actual contract content unless explicitly requested through a content/preview endpoint.

## 9. Frontend: small but convincing demo

Implement a simple, readable React+TypeScript SPA with three areas:

### Documents

- List documents with title, latest revision, processing/search status, dates.
- Create document and upload original PDF/JPEG/PNG.
- Document detail shows metadata, revision history, and an artifact list (kind, MIME, size, hash prefix, source artifact, processor, date).
- Button to process/reprocess an uploaded original; visible job status; refresh/poll while a job is pending.
- Buttons to view/download an artifact. Inline text preview for Markdown/JSON; PDF/image preview if straightforward. If difficult, opening original in a new tab plus snippet/page information is acceptable.
- If more than one representation exists, label them explicitly: original vs derived; extracted Markdown vs normalized Markdown.

### Search

- Text input; mode selector: **Exact / Normalized / Fuzzy**.
- Relation selector: **Contains / Does not contain**. Disable unsupported fuzzy-negative combination with an explanation.
- Fuzzy threshold slider or numeric input (only when relevant).
- Run search, show count and a results table/list: document, revision, page, snippet, match class, score/warning.
- Show **unverifiable** documents separately, especially for negative searches.
- Clicking a result opens document details and, if available, page + matching context.

### Jobs / status

- Show queued/running/completed/failed tasks and error messages.
- Make it obvious whether a document has not been processed, has OCR warnings, or is fully searchable.

No mock data in the actual UI. Placeholder sample cards may be included only in a clearly labeled development story/demo page, not in the real library or search results.

**Usability:** Clearly communicate that "not found in extracted text" is not equivalent to a legal conclusion. Avoid green badges saying a document is "compliant" based solely on substring search.

## 10. Worker and operational behavior

A simple worker may poll `processing_jobs` every short interval. The worker must:

- Claim a queued job transactionally and move it to running.
- Access the source artifact through the storage service.
- Perform processing without blocking API requests.
- Persist artifacts atomically as far as practical and insert new DB records.
- Write searchable content only for the revision being processed.
- Update job status and error details, with logs containing IDs rather than full sensitive contract text.
- Avoid infinite retry loops. A failed job should remain visible and manually retryable.
- Recover or mark stale running jobs after worker crashes, if practical; document any recovery limitation in the MVP.
- Permit a fresh processing run when the normalization rules or OCR engine change, while retaining old artifact provenance.

Keep startup simple with Docker Compose and named volumes:

```text
postgres     PostgreSQL + persisted data
api          FastAPI; backend image
worker       Same backend image, dedicated worker command
frontend     Vite dev server or served build
blob_storage Shared volume mounted in API and worker
```

Provide `.env.example` with DB URL, storage path, upload size limit, OCR languages, optional Docling flag, frontend API URL. No secrets committed. Use health checks where practical.

## 11. Test data and automated checks

## 14. Engineering tradeoffs to explain in the interview

**Why not RAG by default?** The stated task asks whether literal text is present or absent in a contract. Classical full-text matching is deterministic after text extraction; Top-k retrieval is not sufficient to establish absence. RAG may later help compare *meaning*, but that is a different requirement.

**Why PostgreSQL rather than a separate search cluster?** For a bounded prototype, one relational database plus `pg_trgm` supports metadata, provenance, and approximate lexical search. Reassess for large-scale corpus size, throughput, or sophisticated ranking requirements.

**Why keep artifacts rather than only final text?** Original bytes, OCR outputs, Markdown, and normalized text have different purposes. Provenance enables reproducibility, debugging, and reprocessing after a better OCR model becomes available.

**Why document revisions?** A new legal version of a contract is a different content state; a different serialization/OCR conversion is not.

**Why explicit processing status?** A negative search result has little value if the contract is unreadable. The search UI must not silently treat failed OCR as a missing clause.

**Why no cloud requirement in the MVP?** The local stack demonstrates the core logic without credentials. Production deployment can map the API/worker to Azure containers and storage to Azure Blob, with enterprise identity and permission enforcement added in consultation with Riverty.

**Legal/security disclaimer:** Contract review assistance is not legal advice. This prototype should use synthetic/public test data, never casually upload private agreements to an external model, and should not be described as enterprise-ready or legally compliant without security, privacy and retention review.
